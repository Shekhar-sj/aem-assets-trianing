Overview

AEM Assets Migration Training

Migration consultant edition. A day-by-day path from discovery to a validated go-live — strategy, binaries, metadata, the Content Transfer Tool, Bulk Import and the Content Copy Tool. Every reference, assignment and "done when" check a migration consultant needs, in one place.

Version 1.0 (draft) Author TBD Owner ACS, GDC — AEM Competency Company Adobe ACS

Moving a DAM is rarely "copy the files". A successful assets migration is a planned project: you discover what the client really has, choose the right ingestion method per source, clean names and metadata before they land in AEM, prove the approach with a pilot, and then execute, validate and keep the target in sync until cut-over. This program teaches that end-to-end flow for AEM as a Cloud Service (AEMaaCS) Assets targets.

Plan for 3 days (≈ 18–21 h across the days, plus 6–8 h for the capstone). Estimates assume basic AEM Assets familiarity and exclude time waiting on access approvals (Cloud Manager, CAM, Software Distribution).

Your learning path

Six stops from setup to a migrated, validated capstone. Pick any card to jump in — your progress is saved in this browser.

Migration scenarios covered

A · AEM 6.x / AMS → AEMaaCS

Source is an on-premise or Adobe Managed Services AEM (6.3+). Use BPA + Cloud Acceleration Manager + Content Transfer Tool (CTT). Covered on Day 3.

B · External DAM / file store → AEMaaCS

Source is a non-AEM DAM, file share or cloud drive. Stage binaries in Azure Blob / Amazon S3 (or connect Dropbox etc.) and use the Bulk Import tool + metadata import. Covered on Day 2.

C · AEMaaCS ↔ AEMaaCS environments

Not a migration in itself, but used during every migration to refresh lower environments. Use the Content Copy Tool in Cloud Manager (CTT can't copy cloud → cloud). Covered on Day 3.

By the end you will be able to

  • Run an assets discovery workshop and turn the answers into a migration approach and risk list.
  • Choose the right binary ingestion method (CTT, Bulk Import, aem-upload / Asset APIs, manual) using the decision tree.
  • Apply AEM naming rules, folder design and batching guidance before ingestion.
  • Configure, dry-run, schedule and monitor Bulk Import from Azure Blob, S3 and Dropbox.
  • Map, transform and import metadata in bulk with CSV — and know when to do it in code.
  • Run BPA, create migration sets in CAM, extract and ingest with CTT, including top-ups and AzCopy pre-copy.
  • Use the Content Copy Tool safely, and know what it is not for.
  • Validate a migration (counts, size, sampling, hashes, metadata), plan the delta and run the post-migration checklist.

How the assignments work

All assignments build one practice migration for a fictional client, Luma Retail, which is moving to AEMaaCS Assets from two sources: a legacy AEM 6.5 author (scenario A) and a third-party DAM export staged in Azure Blob Storage (scenario B). Keep working in the same environments rather than starting fresh each day — the capstone stitches everything together. Each assignment has a "Done when" check: treat it as the definition of done. Assignments marked (Dev track) are optional for functional consultants.

Our approach (ACS)

The ACS Asset Migration Strategy chooses the approach from three drivers: the asset source, the AEM destination (AMS or Cloud Service) and the business use case. Extracting assets and metadata out of the source system is normally the client's responsibility and out of scope; we own bringing them into AEM, applying metadata, and the design decisions around that.

Discovery

Answer these before choosing a route — each one changes the plan:

  1. Number of assets / nodes — node count drives duration more than size. Example from the field: 4 GB with 50k nodes took longer than 24 GB with 8k nodes. Beyond supported node limits, involve engineering.
  2. Repository size — secondary to node count, but needed for planning and validation.
  3. Source systems — one or many; AEM or non-AEM (another DAM, file shares, drives).
  4. Feature gap — what does the client use today that works differently (or not at all) in AEM Assets?
  5. Downtime & freeze — is a content freeze acceptable, and when? Set expectations on delta migration early.
  6. As-is or filtered — clean up outdated/duplicate assets before migrating (at the source or in temporary S3/Azure storage, not in AEM). Confirm in the SOW who moves assets to temporary storage.
  7. Target hierarchy — same as source, or new? Decide: move after ingestion, ingest via API to target paths, or restructure before ingestion.
  8. Frequency — one-time migration or recurring ingestion?
  9. Naming — special characters, upper-case folders, duplicates, which versions (latest or all).
  10. Metadata — what must be mapped, is it required for all assets, does anything need writing to the binary (XMP)?
  11. File formats — everything can be stored, but not every format gets thumbnails/previews (for example EPS/AI/PSD). Align expectations.
  12. Success KPIs — agree up front: number of assets, size, SHA values, metadata.

For AEM sources also ask about custom Oak indexes, a customised DAM Update Asset workflow, ACS Commons / Asset Share Commons usage, versions, Dynamic Media, Content Fragments in the DAM and the latest BPA report.

Design considerations
  • Folder size — keep folders to about 1,000 direct children. AEMaaCS supports more, but above 1,000 the Admin UI switches to an asynchronously updated listing (new items appear after a short delay).
  • Batches — migrate large volumes in phases, for example 6 TB as 10 batches of 600 GB, or about 50k assets per batch.
  • Offline compaction (AMS/on-prem targets) — compact after every ~50k assets or when throughput drops.
  • Metadata CSV — always UTF-8 so special characters survive.
  • Write-back — decide whether metadata must be written into the binary and whether a custom namespace is needed.
  • Indexes — deploy index changes for business search/filters before migration; reindexing later is heavy.
  • Hierarchy — migration is as-is; restructure before ingestion, move afterwards, or use the APIs.
  • Failures — under 50 failed assets: retrigger manually. Over 50: find the root cause, fix, then re-run.
  • Design Considerations
Naming conventions

AEMaaCS blocks uploads with forbidden characters. Fix names before ingestion — ideally at the source or in the staging bucket.

ItemNot allowed
Asset name* / : [ \ ] | # % { } ? & and ;=
Folder name* / : [ \ ] | # % { } ? " . ^ ; + & and tab — and folders should be lower-case on Cloud Service

What Bulk Import does automatically: asset names are escaped with JcrUtil.escapeIllegalJcrChars (for example new%asset.png → new%25asset.png); folder names go through DamUtil.getSanitizedFolderName (lower-cased, special characters and spaces → -). Names ending in a dot or containing control characters are skipped and marked failed. The original title is kept in jcr:title.

Approaches (preferred first):

  1. Script over the staging bucket (for example an AWS Lambda / Azure Function) that replaces unsupported characters and logs every rename for validation.
  2. Export the file list to CSV, find offending names with a regex, rename by script or by hand.
  3. Let the ingestor sanitise — fine for a small number of files, but you lose an explicit rename log.

Pre-migration checklist
  • Finalise the approach; sanitise names; clean up unwanted assets at the source. Confirm S3/Azure access if your method needs it.
  • Disable workflow launchers and listeners that aren't needed under the migration root (/content/dam/<root>) — this is a code deployment.
  • Put the metadata schema, custom namespaces, metadata profiles and processing profiles on target folders before ingestion.
  • Deploy index changes (for example to damAssetLucene) before ingestion; decide on full-text search in documents (Tika).
  • Decide with the client whether to keep Smart Tags enabled (on by default in AEMaaCS; disabling also disables similarity search).
  • AMS/on-prem targets: lower error.log level on lower environments, optimise or defer DAM Update Asset, and tune the ACS Commons Throttled Task Runner (max threads ≈ cores ÷ 2; default 4).
  • Communicate: authoring freeze for business users; no code or content deployments during migration.
  • Pre-Migration Checklist
  • Sample tasks checklist (AMS → CS)
Proof of Migration (PoM)
  1. Run a pilot on a lower environment (Stage) with production-like content.
  2. Pilot size: 25% of the content or ~1 TB, whichever is less, mixing all content types.
  3. Resolve issues found (disk space, connectivity, ingestion errors).
  4. Time it — for 6.x targets with and without the DAM Update Asset workflow — and extrapolate to a production plan and estimate.
  5. After QA sign-off of the pilot, run the full migration on production author.

For CTT there is no formula for duration: bandwidth, heap, disk I/O and node/blob counts all matter. Run PoMs early and extrapolate.

Knowledge check

Which matters more for migration duration — repository size or node count?

Node count. Many small assets (more nodes) can take longer than fewer large ones.

A folder name in the source is Spring Campaign 2026. What will Bulk Import create?

spring-campaign-2026 — lower-cased, spaces replaced with dashes. The original name is kept as the folder title.

When must processing and metadata profiles be on the target folders?

Before ingestion, so assets are processed correctly on arrival instead of needing reprocessing.

45 assets failed. What do you do? And 400?

Under 50: retrigger them manually. Over 50: investigate the root cause first, fix it, then re-run.

Bulk Import — what it is

The Asset Bulk Import tool is the recommended method for large-scale migrations and occasional bulk ingestions into AEMaaCS from Azure Blob Storage or Amazon S3 (the Assets view also offers sources such as Dropbox). It is available only to the administrators group.

  • Create the container/bucket as private, accepting only authorised requests. Extra network ingress restrictions on the bucket aren't supported.
  • It imports the whole folder structure from the source, but empty folders are not created.
  • Best practice: curate (remove unused/duplicate assets), organise (for example isolate very large files), and stagger ingestions in several jobs.

3.2 Metadata — mapping rules
  • Define the metadata schema, profiles and taxonomy in the target before mapping.
  • Don't migrate system fields — MIME type, size, uploaded date, uploaded by are generated by AEM. Size shows in bytes in AEM even if the source used KB/GB.
  • Tags/keywords and dates usually need reformatting; plan scripts or post-processing.
  • Drop-down values must match exactly (case and spelling) between source and target.
  • Keep legacy fields (legacy upload date/by) read-only; don't reformat them unless business logic uses them.
  • Agree what's extracted from the binary (XMP) and whether anything must be written back.
  • Metadata Mapping

Delta & post-migration

Delta: agree a date and a short content freeze. The source produces a delta report, a delta metadata.csv and the delta binaries in the staging bucket. Run the same pre- and post-migration steps, then retry any failures.

Post-migration checklist:

  • No errors or warnings in the author logs (Cloud Manager log download on AEMaaCS).
  • Re-enable launchers and profiles, and reprocess assets if processing was deferred (AEMaaCS: Reprocess Assets; 6.5: ACS Commons Bulk Workflow, max ~50k paths per run).
  • Restructure folders if the migration was as-is (for example ACS Commons MCP Folder Relocator on 6.x, or move operations).
  • Sample asset-level metadata across categories.
  • Enable Dynamic Media sync if used.
  • Publish in batches by subtree — never activate the DAM root in one go.

Knowledge check

Why prefer a SAS token over an Access Key?

A SAS token can be limited by permissions and expiry. An Access Key grants full access to the storage account.

Your metadata import reports success, but drop-down fields are blank in the UI. What's the likely cause?

The values don't exactly match the schema's drop-down options (case or spelling).

What does "Replace" import mode do to existing metadata and the asset ID?

It overwrites the asset. Existing metadata and edits are lost, and the asset ID is regenerated, which breaks Assets Insights tracking.

Are assets reprocessed automatically after they're ingested with CTT?

No. They are reindexed, but you must request reprocessing.

BPA & CAM readiness

Run the Best Practices Analyzer on the source, export the report as CSV and upload it to your CAM project. Review the code and content complexity findings and turn them into backlog items.

  • Missing original rendition: the binary was never uploaded properly. Back it up, then remove it at the source before extraction, because bad data breaks asset processing.
  • Folders missing jcr:content: profiles and settings won't inherit below them. Fix them before migrating.
  • The internal BPA utility focuses on Asset Content Validator (ACV) findings, such as missing mandatory nodes.
  • Best Practices Analyzer
  • CAM readiness phase
CTT — how it works
CAM projectCreate a migration set and copy its extraction key
Source AEMInstall CTT, paste the key, add paths, run Check Size
ExtractionSource content goes to the migration set (Adobe-provided cloud storage)
IngestionStarted in CAM, from the migration set into the target author or publish
ValidateValidation report and principal migration report
  • Extract once and ingest into several environments in parallel. Ingestion logs are kept in CAM.
  • Groups are migrated, but users are not; users come from IMS. Extraction copies all of /home/groups, and ingestion brings in the groups referenced in the migrated content's ACLs.
  • CTT does no content analysis. It doesn't distinguish published from unpublished content, so run it author → author and publish → publish.
  • CTT supports AEM 6.3+ on-prem or AMS → AEMaaCS only. It cannot move content between Cloud Service environments.

Migration sets
  • Up to 10 migration sets per CAM project, expired ones included. Names follow JCR node naming rules.
  • Choose the region closest to the target environment. It can't be changed later.
  • The extraction key is valid for 14 days and can be renewed. Treat it like a password.
  • A set expires after about 45 days of inactivity. Editing it, getting its key, extracting or ingesting resets the clock.
  • On the source (Operations → Content Migration), paste the key, add include paths (or upload a CSV of paths, one per line, from CTT 3.0.24) and exclude paths (for example /content/dam/luma/archive). /apps, /libs, /home and most of /etc are restricted.
  • Include versions also adds /var/audit.
  • Always run Check Size before extracting. It tells you whether disk space is enough and whether the set is within product limits.
  • Getting started with CTT
Extraction & AzCopy pre-copy
  • Overwrite staging container on = full re-extraction. Off = top-up, which adds only what changed since the last extraction.
  • Pre-copy uses AzCopy to copy blobs directly between stores, which speeds up large first runs. From CTT 2.0.16 it's set up automatically and used whenever the set is over 200 GB. The config lives in crx-quickstart/cloud-migration/azcopy.config.
  • Pre-copy requires data store garbage collection within the last 7 days. A File Data Store also needs free space above 1/256 of the data store size (for example over 11.72 GB for 3 TB). Moving data out of S3 or Azure has egress costs.
  • Watch the extraction log for Beginning AzCopy Pre-Copy phase. If only some blobs fail, re-run with both Pre-copy and Overwrite unchecked.

azCopyPath=/usr/bin/azcopy
azureSas=https://<account>.blob.core.windows.net/<container>?<read-list-SAS>

Ingestion

In CAM, open Content Transfer → Ingestion Jobs → New Ingestion. Pick the migration set, the destination (RDE and Preview environments aren't allowed), the tier, Wipe and Pre-copy.

⚠️

Author ingestion takes the author service down for the whole run; the environment shows as hibernated. Publish keeps serving traffic. Don't run Cloud Manager pipelines during an ingestion.

  • Wipe = on resets the destination, permissions included; re-add yourself to administrators afterwards. Wipe = off keeps existing content as the starting point.
  • Either way, ingestion replaces paths rather than merging them. If the set contains /content/page1, the target's whole page1 subtree is replaced.
  • Non-wipe ingestion is designed for top-ups. Used otherwise, it can be very slow.
  • Starting an ingestion needs AEM administrators membership on the target, or a pasted migration token.
  • An IP allowlist on the target blocks CAM. Add 0.0.0.0/0 temporarily during ingestion and indexing.
  • AEM version updates are paused automatically during ingestion.
  • After ingestion, assets are reindexed but not reprocessed. Request reprocessing yourself.

  • Validating transfers
Top-ups, go-live & Dynamic Media
  • After the first full transfer, run frequent top-ups (extraction with overwrite off, ingestion with wipe off) to shorten the final freeze. Skip pre-copy for top-ups under 200 GB.
  • Don't restructure source content between the initial extraction and later top-ups.
  • If you include versions and top up with wipe=false, disable version purge on the source, or ingest with wipe=true instead.
  • There are no merge ingestions. Consolidate multiple source systems before migrating where you can.
  • Dynamic Media: AEMaaCS supports Scene7 mode only, so hybrid mode must be migrated. Disable DM on any clone used for extraction. At go-live, connect DM on AEMaaCS and disconnect it from the source.
Content Copy Tool

A Cloud Manager feature that copies mutable content between AEMaaCS author services, for example to refresh Stage or Dev with real content after a migration, or for UAT.

  • Permitted paths: /content, /conf/**/settings/wcm, /conf/**/settings/dam/cfm/models, /conf/**/settings/graphql/persistentQueries, /etc/clientlibs/fd/themes.
  • Content set: up to 50 include paths and unlimited exclude sub-paths. Create and edit it under Cloud Manager → Content Sets.
  • Directions: top-down (Prod → Stage → Dev/RDE) and forward flow between non-production environments (for example Dev → Stage). Production is never a forward-flow destination.
  • Options: include ACLs, Wipe destination before import, package import failure policy (stop on first failure or continue), and publish after import (mirrors the source's publish state).
  • Permissions: the Deployment Manager role to manage sets; Deployment Manager and AEM administrators to start a copy.
  • Limits: author only; no concurrent copies per environment; no version history; no automatic delta; not a cloning or backup tool. Never run it while a CTT ingestion is running on the same environment. Cancelling can leave a partial copy.
  • Monitor it under Environments → Copy Content Activity; download the logs for source and destination.
  • The Content Copy Tool

Content Transfer Tool
  • AEM 6.3+ on-prem/AMS → AEMaaCS
  • Large volumes, versions, groups
  • Top-ups to shorten the freeze
Bulk Import
  • Non-AEM sources staged in Azure, S3 or Dropbox
  • One-time or scheduled
  • Metadata through CSV
Content Copy Tool
  • AEMaaCS → AEMaaCS (author)
  • Refreshing lower environments
  • No versions, no delta tracking

  • Small, targeted content
  • Not for bulk asset migration

Knowledge check

A client wants to copy Dev → Prod with the Content Copy Tool. Is that possible?

No. Production is never a forward-flow destination. Content reaches Prod through migration or authoring, not by copying it up from Dev.

With wipe off, will ingesting /content/dam/luma keep target-only assets under that path?

No. Ingestion replaces paths and doesn't merge, so the whole subtree in the migration set overwrites the target's.

The extraction key was generated 16 days ago. What now?

It's expired, because keys last 14 days. Renew it in CAM, then extract.

Ingestion can't reach the migration service, and the target has an IP allowlist. What's the fix?

Temporarily add 0.0.0.0/0 to the allowlist for the ingestion and indexing, then restore it.
